## 候选主要用户

### P1：漏洞/安全运营人员

职责假设：维护资产和漏洞态势、判断风险优先级、协调责任人、跟踪处置并提供报告。

候选问题：

- 数据分散在资产、漏洞、业务、人员、部门和工单系统中；
- 相同对象存在名称、ID 和归属歧义；
- 大量漏洞不能只按严重度逐个处理，需要结合业务重要性和真实利用信息判断；
- 从发现问题到推动责任人处置需要多次查询、解释和状态跟踪；
- 若候选解法包含 AI，其结论必须能查看来源和证据，写操作边界仍由 DG-08 与确定性权限控制。

### P2：资产或业务系统责任人

职责假设：理解自己或本部门负责的资产与漏洞，判断业务影响并完成修复任务。

候选问题：

- 不清楚哪些资产、漏洞和工单真正属于自己；
- 安全术语和通用严重度不能直接说明业务影响；
- 需要明确“为什么优先处理、处理什么、处理后如何证明完成”；
- 希望用业务语言获得结果，而不是理解底层查询字段和多个安全系统。

### P3：安全负责人或管理者

职责假设：了解组织、部门和关键业务的风险，决定资源和优先级，监督处置闭环。

候选问题：

- 难以从大量资产和漏洞明细中快速形成业务风险判断；
- 需要比较部门、负责人和业务系统的暴露与处置状态；
- 需要可信、可复核的摘要和趋势，而不是模型生成的无来源结论；
- 需要知道高风险动作由谁批准、执行了什么以及结果如何。

### P4：审计、合规或风险监督角色

职责假设：复核风险判断、操作授权和处置记录。

候选问题：

- 需要完整但脱敏的任务、证据、审批和处置链路；
- 不能接受原始凭据、prompt 或 provider payload 进入产品输出；
- 需要区分模型建议、人员决策和外部系统真实变更。

## 候选核心 Jobs-to-be-Done

1. 当我需要了解责任范围时，快速识别属于个人、部门或业务系统的资产和漏洞。
2. 当漏洞数量很多时，结合真实利用、资产暴露、业务重要性和当前状态判断处理顺序。
3. 当结论不确定时，查看支持结论的安全事实，并解决人员、部门、资产或漏洞歧义。
4. 当需要推动处置时，把风险转成责任明确、状态可跟踪的任务，并确保高风险变更经过审批。
5. 当需要管理或汇报时，按业务、部门、负责人和风险状态获得一致摘要，并能回看判断与处置过程。
