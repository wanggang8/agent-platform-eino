# PI-005：漏洞直接修复延时

## Background

产品中心／运营将修复延迟标记为最频繁的漏洞例外处置。运营与相关人员人工沟通后，决定某条漏洞需要延长修复期限，并共同确定新期限；目标环境使用运营直接延时并设置新修复期限的路径，不走申请／审批流程。

实际流程一次只处理一条漏洞。FOBrain 源码虽支持批量操作，但该能力不是当前用户流程；直接延时只允许特定原状态进入，每条成功记录会更新漏洞状态与修复期限并写入历史。当前项目没有任何经过 live 验证的漏洞写域能力，不能完成或核验该操作。

该处置每周都会发生，但最近一次从人工沟通到完成操作约几分钟；它是高频、单次耗时低的候选流程。

若未及时完成直接延时，漏洞将不能及时修复。

## Goal

让管理员能够基于运营与相关人员已沟通确定的结果，对一条符合条件的漏洞直接设置新的修复期限，并明确区分延时成功、失败和未处理状态。

不包含延时申请／审批、自动延时、漏洞修复完成或自动催促。

## 业务输入与输出

| 类型 | 内容 |
| --- | --- |
| 输入 | 选择的一条漏洞、其当前状态、新修复期限、可选的延时原因备注。统一漏洞卡片展示 POC、IP、IP 在线／离线状态、业务系统和修复负责人。 |
| 输出 | 延时成功时提示“延时成功”；失败或回读不一致时逐条显示未完成／待排查。不通知当前负责人；操作历史和成功字段明细不在本产品展示。 |
| 候选成功证据 | 回读确认漏洞状态为“延时”、修复期限等于指定新期限。FOBrain 底层操作历史不作为本产品展示或验收项。 |

## 验收标准

### AC-01：合格漏洞可直接延时

Given：一条漏洞处于允许直接延时的状态，运营与相关人员已确定新的修复期限，且管理员完成二次确认。  
When：管理员执行直接延时并完成回读。  
Then：只有该漏洞状态为“延时”且修复期限为指定新期限时，才显示“延时成功”。

### AC-01a：成功仅提示结果

Given：该漏洞状态和修复期限均已通过回读核验。  
When：管理员完成直接延时。  
Then：管理员界面提示“延时成功”，不展示操作历史或成功字段明细。

### AC-01b：成功后不通知负责人

Given：一条漏洞已直接延时成功。  
When：系统完成成功结果反馈。  
Then：系统不向该漏洞当前负责人发送通知。

### AC-02：不合格状态不得写入

Given：一条漏洞不处于允许直接延时的状态。  
When：运营尝试直接延时。  
Then：该漏洞不被修改，并返回可识别的状态不符合原因。

### AC-03：单条操作结果可核验

Given：运营对一条漏洞执行直接延时。  
When：该漏洞不能完成延时或回读结果不一致。  
Then：该漏洞保持未完成状态，并返回可识别的失败原因；不得显示为延时成功。

### AC-04：失败可进入缺陷修复闭环

Given：直接延时写入失败或回读结果不一致。  
When：运营确认该漏洞未完成延时。  
Then：运营联系 FOBrain 系统负责人排查 bug；该漏洞在修复前不得显示为已延时。

### AC-05：备注可选且保留原因

Given：运营已确定一条漏洞需要直接延时。  
When：运营不填写延时备注，或填写人工沟通后确定的延时原因。  
Then：系统均可继续处理；已填写的原因随该次操作保留。

### AC-06：仅管理员可执行

Given：运营与相关人员已完成沟通并确定延时及新期限。  
When：非管理员尝试执行直接延时。  
Then：系统不得写入延时；只有管理员可执行该操作。

### AC-07：写入前必须二次确认

Given：管理员已填写一条漏洞的直接延时信息，且确认页展示统一漏洞卡片内容（POC、IP、IP 在线／离线状态、业务系统、修复负责人）、将设置的新修复期限和可选的延时原因。  
When：管理员尚未完成本产品提供的二次确认，或取消确认。  
Then：系统不得向外部系统写入；只有完成二次确认后才能发起写入。

## 未决项与准入限制

- 新期限的具体约束尚未获得用户证据。
- 该动作每周发生、单次约几分钟；未及时延时会使漏洞不能及时修复。它纳入本轮实验范围，但不以此推导生产价值承诺。
- 目标部署的允许状态集合和写入回读接口尚未验证；本产品不新增通知能力。
- 当前项目没有漏洞写域 capability 的 live 证据；在完成动作边界、授权、审计、回读核验与失败补救前，不得实施。
