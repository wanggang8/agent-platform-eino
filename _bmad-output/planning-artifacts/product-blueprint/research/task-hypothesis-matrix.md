# 第一个 FOBrain 业务样本的单任务假设矩阵

## 用途与边界

本矩阵把历史的 24 个工具重新组合为可让真实用户验证的**首个样本单任务假设**。FOBrain 不是最终产品边界。本矩阵不是需求清单、Product Issue、MVP 范围或产品定位；任何任务在获得真实用户证据前都不能进入 final PRD。

FOBrain 官方页已核对：FOBrain 自身已经声明覆盖多源资产关联融合、可信资产清单、漏洞去重归一、动态优先级排序以及漏洞闭环处置。因此，下面要验证的是用户使用 FOBrain 后仍然存在的剩余任务，以及任一候选解法相对现状的可测增量；不得把上述厂商声明范围重新包装成新产品价值。[FOBrain 官方产品页](https://www.huashunxinan.net/product-fobrain)

所有 `T-*` 当前共用完整 canonical record：`MULTIPLE_SOURCES / SYNTHESIS / UNKNOWN / SOURCE_ONLY / HYPOTHESIS / NOT_NORMATIVE`，因为每项都混合了归档历史线索、FOBrain 厂商声明与研究推演。后文 `L0～L2` 只表示**历史材料覆盖度**，不是证据状态、不能升级目标适用性，也不参与 DG-04 通过判定：

- `L2（中低）`：历史能力和接口能组合出任务主要事实，但没有用户频率、成本或对照实验。
- `L1（低）`：仅能支持任务的一部分，关键事实、动作或真实样本缺失。
- `L0（不足）`：当前历史边界不能产生任务要求的业务结果，只能用于发现性访谈。

当前不存在 `L3/已验证` 任务；历史工具存在不等于用户需要该任务。

## 候选任务

### T-01 核对“我／本部门现在负责什么风险”

| 字段 | 假设内容 |
| --- | --- |
| 候选用户 | 资产／业务系统责任人；次要候选为需要代查责任范围的漏洞运营人员。角色均未确认。 |
| 触发／输入 | 日常开始工作、收到安全通知或被追问整改状态时；输入为当前登录身份，可选部门、关键词、严重度或时间范围。 |
| 期望业务输出 | 一份权限范围内的资产、漏洞、重要业务和待处理工单概览；同时说明归属依据、歧义、缺失和无权限项。它不应自行创造新的风险优先级。 |
| 现状替代 | **待用户确认：**在 FOBrain 的资产、漏洞、业务和工单页面分别筛选，使用“我的”视图，导出后拼接，或请安全人员代查。 |
| 历史能力组合 | `current_user_context` + `my_permissions` + `my_assets` + `my_vulnerabilities` + `my_business_systems` + `my_important_business_systems` + `pending_tickets`；不是七个独立需求。 |
| 与 FOBrain 重叠 | **厂商声明范围高重叠。** 是否有增量只能由 DG-05 后的中立解法对照证明，不能预设 AI。 |
| 可行性限制 | 归档样本曾记录用户响应无显式部门、`staff_ids` 为空和姓名 fallback 风险；归档计划还记录当时缺待处理工单样本。目标部署当前状态未知。 |
| 历史材料覆盖度（非 canonical） | `L1（低）`：查询入口较多，但稳定身份映射和真实工单证据不足，也没有任务频率证据。 |
| 最小用户验证问题 | “请展示你最近一次确认自己或本部门要处理哪些安全问题的全过程：从什么事件开始、打开了哪些页面、问了谁、怎样判断没有漏项？” |
| 若成立的可测指标 | 端到端完成时间、页面／导出／人工询问次数、责任范围误归属率、漏项率、需要升级给安全人员的比例。先测基线，不预设达标值。 |

### T-02 对一个 IP／资产形成可复核的风险调查包

| 字段 | 假设内容 |
| --- | --- |
| 候选用户 | 漏洞／安全运营人员；也可能是被通知后自行核查的资产责任人。 |
| 触发／输入 | 告警、外部暴露发现、责任人询问或排障时；输入为 IP、资产 ID 或可消歧的资产标识。 |
| 期望业务输出 | 同一任务内汇集资产基本事实、关联漏洞、责任关系、已知状态、证据时间和未知项，形成可复核的只读调查包；不代替人员作最终处置决定。 |
| 现状替代 | **待用户确认：**在资产页、漏洞页和详情页之间来回查询，把结果复制到笔记、截图、表格或即时通信中。 |
| 历史能力组合 | `list_assets_by_ip` + `list_vulnerabilities_by_ip` + `get_asset_detail` + `get_vulnerability_detail`，必要时结合 `threat_relevance_list`；IP 查询已有较明确接口映射。 |
| 与 FOBrain 重叠 | **厂商声明范围高重叠。** FOBrain 官方声称覆盖资产清单、资产关系与攻击面管理；目标部署与任务效果未知，必须按所选 A/B 路径对照“单任务调查结果”与实际原生流程。 |
| 可行性限制 | 历史资料列出的安全事实字段较窄；资产—漏洞—业务—责任人的稳定跨对象标识、深链接、数据时间和冲突语义尚未证明，历史变化也未证明。 |
| 历史材料覆盖度（非 canonical） | `L2（中低）`：IP、资产和漏洞查询／详情的历史映射相对完整，但没有真实用户任务与现有 FOBrain 同任务基线。 |
| 最小用户验证问题 | “请选最近一次由某个 IP 或资产触发的真实调查，边做边说明：为了回答‘它是什么、有什么风险、谁负责、下一步是什么’，你分别去哪里找了哪些事实？” |
| 若成立的可测指标 | 调查总耗时、页面切换与复制次数、关键事实完整率／正确率、证据来源可定位率、因缺失或错配导致的返工次数。 |

### T-03 对一个已知漏洞／CVE 确认影响范围与责任人

| 字段 | 假设内容 |
| --- | --- |
| 候选用户 | 漏洞运营人员、安全分析员；协作候选为资产／业务责任人。 |
| 触发／输入 | 收到热点漏洞、监管通报或内部漏洞名称／ID 后；输入为漏洞名称、漏洞 ID 或 CVE，可选业务、IP 或范围条件。 |
| 期望业务输出 | 受影响资产清单、已知负责人／部门、相关业务、当前状态和未能关联的对象，并明确数据来源与更新时间；不把“查到”自动等同于“必须立即修复”。 |
| 现状替代 | **待用户确认：**使用 FOBrain 搜索／关联页和多个筛选器，导出后按资产、人员或部门再次核对，再通过表格或消息通知责任人。 |
| 历史能力组合 | `get_vulnerability_detail` + `threat_relevance_list` + 按 IP／负责人／部门查询资产与漏洞；必要时结合 `external_high_risk_assets` 和业务查询。 |
| 与 FOBrain 重叠 | **厂商声明范围很高。** FOBrain 已声明漏洞归一、验证、动态优先级和闭环；候选增量只能通过真实任务证明，不能声称重新提供漏洞管理。 |
| 可行性限制 | 归档资料曾列出 `threat_relevance_list` 接口映射，但责任人与业务关系的完整性、稳定 ID、真实利用信息、数据时效和目标代表性未证明；姓名 fallback 只是待核验风险。 |
| 历史材料覆盖度（非 canonical） | `L2（中低）`：漏洞详情和关联列表有直接历史映射，跨对象责任链与用户价值仍未验证。 |
| 最小用户验证问题 | “最近一次收到重要漏洞通知后，你怎样确认受影响资产和责任人？请展示每一步，以及最容易漏掉、误归属或反复确认的地方。” |
| 若成立的可测指标 | 从漏洞输入到可交付影响清单的时间、受影响资产召回率／准确率、责任人映射准确率、未关联对象比例、人工二次核对次数。 |

### T-04 解释 FOBrain 现有风险／优先级结论“为什么现在处理”

| 字段 | 假设内容 |
| --- | --- |
| 候选用户 | 需要做优先级判断的漏洞运营人员；需要接受处置要求的资产／业务责任人。 |
| 触发／输入 | 对某漏洞、资产或业务的处置顺序存在质疑，或需要向责任人说明原因时；输入为 FOBrain 中已有对象与优先级／风险结果。 |
| 期望业务输出 | 只解释现有结论所依赖的可见事实、来源、时间、适用范围、推断和未知，不另算一个竞争性风险分，也不把模型意见伪装成 FOBrain 事实。 |
| 现状替代 | **待用户确认：**查看详情字段和排序结果后，由安全人员凭经验口头解释、截屏说明，或查外部漏洞情报补充理由。 |
| 历史能力组合 | `get_vulnerability_detail` + `get_asset_detail` + `business_risk_summary` + `external_high_risk_assets` + `threat_relevance_list` + 状态统计。 |
| 与 FOBrain 重叠 | **厂商声明范围直接重叠。** FOBrain 已声明 VPT 动态优先级排序；候选任务只能验证“解释既有排序”是否解决真实沟通／复核成本，不能承诺更好的排序。 |
| 可行性限制 | 归档资料没有 VPT 输入项和规则证据，并把业务风险来源主要映射为统计 bucket；目标部署的解释字段、责任、业务重要性、暴露、时间序列和真实利用信息未知。 |
| 历史材料覆盖度（非 canonical） | `L1（低）`：历史材料包含部分事实线索，但不足以稳定重建现有优先级依据；也没有“解释困难”的用户证据。 |
| 最小用户验证问题 | “请展示最近一次你必须向别人证明某项风险应优先处理的案例：对方追问了什么，你用了哪些证据，FOBrain 哪些信息足够／不够？” |
| 若成立的可测指标 | 准备解释所需时间、可追溯陈述比例、事实引用错误率、接收方正确复述率、因证据不足产生的往返次数、最终被纠正／推翻的比例。 |

### T-05 为一个关键业务系统准备可核对的风险简报

| 字段 | 假设内容 |
| --- | --- |
| 候选用户 | 安全负责人、漏洞运营人员或业务系统责任人；谁实际制作和消费简报尚未确认。 |
| 触发／输入 | 例会、专项检查、事件响应或业务负责人询问时；输入为业务系统名称、时间范围和关注问题。 |
| 期望业务输出 | 基于可见统计与对象事实的简短风险摘要、关键发现、证据引用和未知项；区分上游统计与 AI 解释，不虚构趋势或结论。 |
| 现状替代 | **待用户确认：**FOBrain 页面／报表、导出表格、人工汇总后编写邮件、即时消息或汇报材料。 |
| 历史能力组合 | `business_list` + `business_risk_summary` + `my_important_business_systems` + `vulnerability_status_summary` + `vul_stats`，按需下钻详情／关联列表。 |
| 与 FOBrain 重叠 | **厂商声明范围高重叠。** FOBrain 官方声称覆盖资产风险与漏洞处置；目标部署与任务效果未知，只有实测证明临时问题回答、证据化叙述或简报制作成本改善才可能构成增量。 |
| 可行性限制 | 历史业务风险接口主要输出聚合 bucket；没有已验证的趋势、目标、基线、业务影响定义、例外和管理口径，不能承诺管理判断。 |
| 历史材料覆盖度（非 canonical） | `L1（低）`：历史材料存在聚合和业务查询映射，但“简报”任务、消费角色与质量标准无用户证据。 |
| 最小用户验证问题 | “请拿最近一次针对某业务系统的风险汇报，从收到要求到发出结果完整演示；哪些内容是系统直接给的，哪些要手工解释或反复核对？” |
| 若成立的可测指标 | 简报准备时间、手工复制／改写次数、可追溯陈述比例、事实更正数、收件人追问次数、同口径复现率。 |

### T-06 把一次调查结果交接给责任人

| 字段 | 假设内容 |
| --- | --- |
| 候选用户 | 发起交接的漏洞／安全运营人员；接收者为资产或业务责任人。 |
| 触发／输入 | 完成初步调查、需要责任人处理或补充信息时；输入为选定资产、漏洞、责任人候选与调查证据。 |
| 期望业务输出 | 一份只读交接包：发生了什么、为什么需要关注、证据在哪里、哪些信息未知、希望接收者完成什么；默认不创建第二套风险案件或工单。 |
| 现状替代 | **待用户确认：**复制 FOBrain 链接／截图／导出到工单、邮件或即时通信，由接收者再次查找上下文。 |
| 历史能力组合 | 资产／漏洞／业务查询与详情 + 责任范围查询 + `pending_tickets`；历史唯一写动作只够更新既有工单状态，不能支撑完整交接流程。 |
| 与 FOBrain 重叠 | **高。** FOBrain 已声明漏洞闭环；必须先证明现有闭环中的交接内容或上下文恢复确有缺口，且交接包不制造第二套状态。 |
| 可行性限制 | 归档资料没有创建／分派／评论／截止期／升级接口证据，也未证明安全深链接、稳定责任人 ID 和接收确认；在 DG-08 前只能以影子方式评价交接内容，目标能力未知。 |
| 历史材料覆盖度（非 canonical） | `L1（低）`：历史材料可组合部分调查事实，但真正的协作动作和闭环对象缺失。 |
| 最小用户验证问题 | “请展示最近一次把风险交给责任人的原始消息或工单（可脱敏）：接收者后来又问了什么、哪些字段需要重查、哪里最容易扯皮或错交？” |
| 若成立的可测指标 | 准备交接时间、接收者补问轮次、误交／退回率、从交接到首次有效动作的时间、交接内容事实更正率。 |

### T-07 人工确认后更新一个既有工单的状态

| 字段 | 假设内容 |
| --- | --- |
| 候选用户 | 有权更新工单的安全运营人员或资产责任人；审批人与执行人是否分离尚未确认。 |
| 触发／输入 | 已有工单进入 `in_progress`、`fixed`、`ignored` 等状态时；输入为工单引用、目标状态和影响摘要。 |
| 期望业务输出 | 在执行前展示准确影响并获得有效批准；批准后仅更新一次，拒绝／取消不变更，结果可核对。 |
| 现状替代 | **待用户确认：**在 FOBrain 现有工单页面直接选择状态，或由他人代为更新。若现有操作已足够快，AI 不应介入。 |
| 历史能力组合 | `pending_tickets` + `update_ticket_status` + 审批、拒绝和幂等边界；这是一个任务链，不是把审批机制本身当用户任务。 |
| 与 FOBrain 重叠 | **厂商声明范围完全重叠。** FOBrain 官方声称提供闭环处置；目标部署、API 和任务效果未知，只有中立方案实测按所选 A/B 规则胜出时才可能保留。 |
| 可行性限制 | 归档计划曾记录当时没有代表性待处理工单样本；归档契约只陈述一个状态更新动作，不证明目标部署当前能力，也不包含创建、回滚、修复执行或结果验证。 |
| 历史材料覆盖度（非 canonical） | `L1（低）`：历史契约有明确陈述，但真实样本、必要性和相对现有页面的增量均缺失。 |
| 最小用户验证问题 | “请展示最近一次状态更新的实际触发、步骤、权限、错误风险和失败后的补救；现有方式哪里足够、哪里不足？” |
| 若成立的可测指标 | 更新完成时间、误选状态率、重复执行率、审批拒绝／修改率、失败后恢复成功率；任何未经批准的真实变更都应单独记录为停止信号。 |

### T-08 验证“工单已关闭”是否真的意味着风险消除

| 字段 | 假设内容 |
| --- | --- |
| 候选用户 | 漏洞运营人员、风险监督／审计角色；也可能由资产责任人自证。 |
| 触发／输入 | 工单被标记 `fixed`／关闭、复测窗口到达或风险复现时；输入为工单、漏洞和资产引用及当前观测。 |
| 期望业务输出 | 把工单状态与当前资产／漏洞事实分开呈现，并按关闭原因给出可核对结局，例如“修复已验证”“风险仍存在”“已缓解但未消除”“已授权接受”“不适用／误报”“延期且仍受控”或“证据不足”；不把关闭状态自动解释为风险消除。 |
| 现状替代 | **待用户确认：**重新扫描、再次查询漏洞状态、让责任人提供证明，或人工对照工单与资产／漏洞页面。 |
| 历史能力组合 | 工单读取／状态 + `get_vulnerability_detail` + 按 IP 查询漏洞 + 状态汇总；只能看到片段，不能证明完整复核链。 |
| 与 FOBrain 重叠 | **厂商声明范围高重叠。** FOBrain 官方声称提供完整闭环；目标部署、集成和任务效果仍未知，应先核对实际复核机制，只有真实“假关闭／复现”问题存在时才继续。 |
| 可行性限制 | 归档资料没有修复证据、复测结果、状态历史、截止期、复发或例外数据的可靠接口证据，并记录当时缺真实工单样本；目标部署当前状态未知。 |
| 历史材料覆盖度（非 canonical） | `L0（不足）`：历史材料不能证明可交付预期结果，只适合用访谈发现问题和核对 FOBrain 既有闭环。 |
| 最小用户验证问题 | “最近一次你如何证明一个漏洞真的修好了？工单关闭后还需要查什么，出现过多少次关闭但风险仍在或无法证明的情况？” |
| 若成立的可测指标 | 按关闭原因匹配正确证据的比例、完成复核所需时间、证据齐全率、不一致状态检出率、需要人工追证的比例；在接口补证前不设产品目标。 |

## 历史材料覆盖度较高的三个访谈探针

这不是研究顺序、DG-04 候选优先级或首版范围。只有当 DG-03 队列的真实事件自然命中时，才可用这些探针追问；研究员不得先展示任务名称要求参与者认领：

- **T-02 单 IP／资产风险调查**：历史查询与详情线索相对多，但目标部署与用户任务未知。
- **T-03 单漏洞／CVE 影响面确认**：历史上有明确输入／输出线索，但跨对象责任链与实际后果未知。
- **T-04 解释现有优先级**：数据与信任风险较高；在 VPT 因素不可见时只能记录未知，不能承诺解释。

先让目标用户用最近发生的真实案例展示现有流程；样本冻结后，只有任务通过 Owner 预注册的“高频效率型”或“低频高损失型”准入路径，才由 DG-04 选为唯一任务，并在 DG-05 后做同规则方案对照。若现有 FOBrain 页面、保存视图、筛选、报表、配置或培训已经按预注册规则完成任务，应停止对应假设，而不是继续恢复更多工具。

## 任务级进入下一阶段的共同门禁

每个任务只有同时补齐以下证据，才可以被考虑升级为需求候选：

1. 至少一类明确执行角色，以及近期真实任务样本；
2. 触发、输入、期望业务输出、结束证据和最终责任人；
3. 当前步骤、替代工具、原始频率、总耗时、等待、实际失败后果和可评价性基线；
4. FOBrain 现有能力、配置／培训和最小非 AI 改进逐项对照，明确剩余问题而不是功能重复；
5. 所需字段、权限、时效、错误语义和真实样本可用性；
6. 通过 DG-04 只选择 A 高频效率型或 B 低频高损失型，并在 DG-05 预注册相应结果与保护指标后，才比较原生增强、AI、独立 Workbench、非 AI 改进和“不做”；A 看效率与质量保护，B 看高损失结果与严重错误保护；
7. 若 AI 形态胜出，事实、推断、未知和外部动作责任可被用户正确识别；若非 AI 或“不做”胜出，则停止 AI 需求升级。

在此之前，八项全部保持 `HYPOTHESIS`，不得转换成 Product Issue 的 Background、Goal 或 Acceptance Criteria。
