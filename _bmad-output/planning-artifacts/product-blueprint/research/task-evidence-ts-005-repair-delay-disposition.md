## 2. 源码发现的两条互斥流程

| 流程 | 源码可证实的行为 | 关键差异 |
| --- | --- | --- |
| A. 直接延时操作 | 批量状态操作可将合格漏洞设为“延时”，更新 `limit_date`，校验原状态并写入操作历史。 | 运营／有权人员直接改变状态和期限。 |
| B. 延时申请与审批 | 申请人提交未来的期望日期，漏洞进入“待审批”；具有“审批延时”权限的人员批准或拒绝。批准后更新 `limit_date`，拒绝则保留原期限。 | 两个角色、审批状态、批准／拒绝回执及权限控制。 |

这两条流程的用户、输入、权限、完成条件和安全边界不同；在目标环境实际路径确认前，不得合并为一个 Product Issue。

## 2.1 已确认实际路径

目标环境确认使用 **A. 直接延时操作**：运营直接设置延迟和新的修复期限，不走“申请延时→审批通过／拒绝”流程。

这使以下内容成为 TS-005 的候选事实：

| 项目 | 当前结论 |
| --- | --- |
| 业务参与角色 | 产品中心／运营，与相关人员沟通并提供业务判断。 |
| 执行权限 | 仅管理员可执行直接延时写入。 |
| 业务触发 | 运营与相关人员人工沟通后，决定该漏洞需要延长修复期限。 |
| 新期限来源 | 运营与相关人员人工沟通后共同确定；不由系统规则自动计算。 |
| 实际操作单位 | 一次只对一条漏洞执行直接延时。 |
| 延时备注 | 非必填；填写时记录人工沟通后确定的延时原因。 |
| 写入确认 | 管理员执行前必须进行二次确认；统一漏洞卡片展示 POC、IP、IP 在线／离线状态、业务系统和修复负责人，确认页在此基础上展示将设置的新修复期限和可选的延时原因。这是本产品默认控制，不是 FOBrain 原有能力。 |
| 写入结果 | 漏洞状态变为延时，修复期限变为运营指定的新期限。 |
| 成功提示 | 管理员完成二次确认且回读核验成功后，界面提示“延时成功”；不额外展示字段明细或操作历史。 |
| 成功后通知 | 不通知该漏洞当前负责人；FOBrain 底层通知能力不属于当前产品流程。 |
| 失败处置 | 写入失败或回读结果不一致时，运营联系 FOBrain 系统负责人排查 bug；该漏洞在修复前不视为已延时。 |
| 任务频率 | 每周都会发生。 |
| 最近单次耗时 | 从人工沟通到完成直接延时操作约几分钟。 |
| 未及时处置后果 | 漏洞不能及时修复。 |
| 历史展示 | 本产品不向用户展示直接延时的操作历史；FOBrain 底层是否记录历史不改变此产品输出边界。 |
| 不适用范围 | 延时申请、审批角色、批准／拒绝结果不属于当前 TS-005。 |
| 仍待确认 | 新期限的具体约束、成功回读的展示方式、频率／耗时及安全后果。 |

## 2.2 源码直接延时契约

| 项目 | 源码事实 | 对 Product Issue 的约束 |
| --- | --- | --- |
| 输入 | 支持批量漏洞 ID、`limit_date`、备注、通知和超时通知等字段。 | 业务必须定义新期限和备注的来源；不能由模型静默编造。 |
| 合法原状态 | 仅待修复、转交、已延时、超时、复测未通过或催促等状态可直接延时。 | 必须在写入前显示／校验不合格项。 |
| 成功写入 | 先把漏洞的 `limit_date` 改为输入值，再写历史并更新状态为“延时”。 | 成功不只是 HTTP 成功；至少需回读状态、期限和历史事实。 |
| 批量失败 | 源码逐条处理并累计失败数；存在失败时返回“批量处理 N 条，失败 M 条”。 | 必须逐项标出成功／失败，不能将部分成功标为全部完成。 |
| 通知 | 处理成功后会按接收人聚合 webhook／站内通知。 | 通知成功不等于延时状态变更成功，需与写入回读分开。 |
