## 1. 用户、任务与真实工作节奏

### 产品中心／运营

- 在 FOBrain 当前账号的内置权限范围内查看和处置漏洞；产品不得扩大权限或把查不到的对象视为可操作对象。
- 每日检查全部新增漏洞，依据漏洞事实自行决定接收人。通常每日需手动派发 100 多条，最近一次约耗时半天；这是首轮高价值主流程。
- 主动转发责任人是独立人工动作，不依赖自动识别错派或其他动作。每周约 20～30 次，最近一次约耗时 10 分钟；未及时转发会造成漏洞修复滞后。
- 误报判断由操作人本人作出，发生频率不固定，单次约几分钟；不及时处理只会使漏洞持续显示为未处理。
- 修复延时先由运营与相关人员在线下人工沟通并确定新期限；产品不负责沟通、判断是否延时或决定期限。

### 管理员

- 是直接修复延时的唯一执行角色。
- 一次只处理一条漏洞；填写新期限，原因可选，然后二次确认并执行。

### FOBrain 系统负责人

- 不是日常操作角色，而是写入失败、回读不一致或系统异常时的排查归属。
- 产品只需让失败对象和原因可识别；不建设缺陷提报、通知或工单闭环。

### AI 的角色边界

- AI 组织已授权事实、展示待操作对象并约束流程。
- AI 不决定接收人、不判断误报、不决定是否延时或新期限，也不得自行写入。
- “没有待派发漏洞”必须来自接口真实空结果，不能由模型自行归纳或虚构。

## 2. 每个明确流程步骤

### 2.1 跨动作共同闭环

1. 当前用户进入自己被授权的事实范围。
2. 产品取得安全、结构化的漏洞事实；不得把 provider 原始返回直接用于界面、审计或模型上下文。
3. 产品在列表／操作准备、二次确认和结果阶段复用同一套统一漏洞卡片事实。
4. 操作人查看事实并自行作出业务决定。
5. 产品准备变更，但尚不向 FOBrain 写入。
6. 产品逐条展示即将被修改的对象和目标变化，等待执行人二次确认。
7. 操作人取消或未确认时结束流程，外部写入数必须为零。
8. 操作人确认后，产品才可发起受控写入。
9. 写入后重新读取外部事实；接口返回成功本身不能决定产品成功。
10. 产品依据每条漏洞的回读结果分别结算成功、失败或待排查。
11. 失败、部分失败或回读不一致的对象保持未完成，并由操作人联系 FOBrain 系统负责人排查。
12. 产品不发送消息、邮件、webhook、催办或通知中心通知；FOBrain 自身通知不是产品成功条件。

### 2.2 每日新增漏洞手动派发

1. 运营执行每日新增漏洞检查。
2. 产品读取当前用户可见的**全部且仅限新增状态**的漏洞，按发现时间倒序展示。
3. 若接口成功且返回 0 条，显示“没有待派发漏洞”。
4. 运营逐条查看 POC、IP、IP 在线／离线状态、业务系统、当前修复负责人；为派发判断还查看业务系统负责人和运维负责人。
5. 运营从 FOBrain 全部人员列表中选择具体接收人；AI 不推荐或替代决定。
6. 运营可以继续逐条判断；只有最终接收人相同的漏洞可以合并为一次派发，不同接收人不得混合。
7. 二次确认时逐条展示统一漏洞卡片和将要指定的负责人，不得只显示数量。
8. 确认后执行派发，并逐条回读当前修复负责人。
9. 只有接口成功且负责人已变为指定人员的漏洞显示完成；其余逐条显示未完成／待排查。

### 2.3 责任人转发

1. 操作人在接口内置权限返回的漏洞中主动选择一条或多条需转发漏洞。
2. 产品不要求先发生错派检测、首次派发失败或其他联动动作。
3. 操作人查看统一漏洞卡片，并从 FOBrain 全部人员列表选择接收人。
4. 仅最终接收人相同的多条漏洞可合并转发；不同接收人必须拆分。
5. 二次确认时逐条展示统一卡片及目标接收人。
6. 确认后执行转发，并逐条回读修复负责人。
7. 只有负责人已变为指定人员才显示转发成功；其他对象逐条显示待排查。

### 2.4 直接修复延时

1. 运营与相关人员在产品之外沟通，人工决定一条漏洞需要延时及其新修复期限。
2. 管理员选择这一条漏洞；该流程不得批量处理。
3. 产品展示统一漏洞卡片、漏洞当前状态、新期限输入和可选原因。
4. 若漏洞不处于允许直接延时的状态，不得写入，并返回可识别的状态不符合原因。
5. 管理员进入二次确认，查看统一卡片、将设置的新期限和可选原因。
6. 管理员取消或未确认时不得写入；确认后才执行。
7. 产品回读漏洞状态和修复期限。
8. 仅当状态为“延时”且期限等于指定新期限时，提示“延时成功”；成功界面不展示操作历史或成功字段明细。
9. 写入失败或任一回读目标不一致时保持未完成，显示可识别失败原因并进入待排查。

### 2.5 误报标记

1. 操作人确认一条漏洞属于自己负责，并人工判断其为误报。
2. 产品只准备这一条漏洞的误报变更，不把判断扩展成规则或其他漏洞的自动修改。
3. 二次确认时展示统一漏洞卡片和将变更为“误报”的状态。
4. 取消或未确认时不得写入；确认后才执行。
5. 产品回读漏洞处置状态。
6. 仅当回读状态为“误报”时显示标记成功；其他结果保持未完成并进入待排查。

## 3. 必须呈现的行级事实

### 所有漏洞动作共用

- POC。
- IP。
- IP 在线／离线状态。
- 业务系统。
- 当前修复负责人。
- 当前操作的逐条状态：准备中的目标变化，或执行后的成功／失败／待排查结果。

这些事实必须在列表／操作准备、二次确认和最终结果中保持同源；不得为不同产品出口维护平行事实模型，也不得用汇总数量替代待写对象明细。

### 手动派发额外判断事实

- 业务系统负责人。
- 运维负责人。
- 从 FOBrain 全部人员列表选择的目标负责人。
- 发现时间，用于验证和呈现倒序队列。

### 转发额外事实

- 从 FOBrain 全部人员列表选择的目标负责人。

### 直接延时额外事实

- 当前漏洞状态。
- 将设置的新修复期限。
- 延时原因；可为空，填写时需随本次操作保留。

### 误报额外事实

- 将变更为“误报”的目标状态。

### 真实数据覆盖边界

- 目标部署实测 628 条新增漏洞中，POC、IP、IP 在线／离线状态、发现时间均无缺失。
- 628 条新增漏洞的当前修复负责人全部缺失；新增态应稳定呈现为空或未分配，不能被模型补全。
- 业务系统缺失 6 条、业务系统负责人缺失 532 条、运维负责人缺失 423 条；缺失必须可见，不能由模型推断。
- 人员列表实测 243 人，人员 ID、名称、状态均无缺失。来源只确认“全部人员列表可读”，没有确认任何前端搜索、筛选或排序规则。

## 4. 状态事实与尚未定义项

| 状态 | 已确认 UX 事实 | 尚未定义、不得擅自补全 |
| --- | --- | --- |
| 空结果 | 新增漏洞请求成功且为 0 条时显示“没有待派发漏洞”；必须与请求失败区分。 | 转发、误报、延时入口的空状态文案未定义。 |
| 加载中 | 来源没有定义加载反馈、刷新时机、分页加载或长操作进度。 | 加载表现、超时前反馈、刷新策略均需 UX 决定。 |
| 无权限 | 产品必须把无权限与空结果、数据不足、外部失败区分；非管理员不得执行直接延时。 | 无权限文案、是否隐藏或展示不可执行动作、如何返回当前流程均未定义。 |
| 字段缺失 | 当前负责人可呈现为空／未分配；业务系统及两类负责人允许为空；不得推断。 | 空值的统一文案、空白与“未分配／未知／数据缺失”的区别尚未最终确定。 |
| 数据不足 | 必须与空结果、无权限和外部失败区分。 | 触发判定、文案和是否阻止不同动作尚未定义；派发所需判断事实大量缺失，不能默认仍可执行。 |
| 查询／外部失败 | 不得伪装成空结果；provider 错误需要安全、脱敏地进入产品事实。 | 用户可见错误层级、恢复入口和重试策略未定义。 |
| 状态不允许 | 直接延时遇到不合格原状态时禁止写入，并给出可识别原因。 | 允许状态集合及具体文案尚未由目标部署验证。 |
| 写入失败 | 该漏洞保持未完成／待排查，不得显示成功；操作人联系 FOBrain 系统负责人。 | 是否提供重试、如何防重复提交尚未定义。 |
| 部分失败 | 合并派发／转发必须按漏洞逐条结算；同批成功项可以完成，失败项逐条待排查。 | 批次级摘要、失败项后续操作和重新组合方式未定义。 |
| 回读不一致 | 即使写接口成功，只要负责人／状态／期限未达到目标，该条仍为未完成／待排查。 | 回读等待时的中间态、回读次数、超时和人工重查入口未定义。 |
| 成功 | 派发／转发以负责人变更为准；误报以状态为“误报”为准；延时以状态和期限同时匹配为准。 | 除“延时成功”外，其他动作的最终成功提示文案未定义。 |

## 5. 二次确认与安全边界

- 所有修改数据的动作均必须由实际执行人二次确认；这不是可跳过的体验选项。
- 确认前只能准备变更，不能发生任何 FOBrain 外部写入。
- 取消确认与未完成确认的结果相同：零写入。
- 确认内容必须逐条列出统一漏洞卡片和该条目标变化，不能只显示选中数量。
- 派发／转发确认必须展示目标负责人；合并操作只允许单一共同接收人。
- 延时确认必须展示新期限和可选原因，并且一次只能确认一条。
- 误报确认必须明确展示将变更为“误报”。
- AI 不能代替执行人完成选择、判断或确认，也不能根据自然语言暗示自动写入。
- 成功必须由安全的回读事实决定，不能使用接口“成功”消息、模型总结或 FOBrain 通知代替。
- 所有外部输入与回读均是不可信数据，进入界面前必须经过安全结构化投影；原始 provider payload 不进入产品层。
- 写失败、部分失败和回读不一致不得被批次成功掩盖，必须逐条保留待排查对象。
- 产品不得扩大 FOBrain 权限，不得提供手工输入姓名代替全员列表，也不得查询／操作当前用户不可见对象。
- 产品不新增任何通知能力。
- 当前门禁只允许实现精确新增、全部人员列表和统一卡片的只读事实链。四类写动作可作为 UX 目标流程被定义，但在 `G-FACT-01`、适用的 `G-WRITE-*` 与 `G-SAFE-01` 通过前不得启用或实施真实外部写入。

## 6. 可推导的桌面端界面表面清单

以下是由明确任务闭环要求推导出的**功能表面**，不决定它们采用独立页面、面板、弹层、抽屉或同页状态，也不决定表格／卡片布局。

| 表面 | 必须承载的任务 | 证据成熟度 |
| --- | --- | --- |
| 新增漏洞队列 | 精确展示全部新增漏洞、发现时间倒序、统一行级事实、选择待派发对象、真实空结果。 | 目标部署读取已验证；当前产品 capability 与 Product Facts 未实现。 |
| 统一漏洞事实呈现 | 在列表／准备、确认和结果阶段复用 POC、IP、在线状态、业务系统、修复负责人，并显式处理缺失值。 | 内容已确认；产品行级投影阻塞。没有证据要求必须单独建设“详情页”。 |
| 人员选择表面 | 从 FOBrain 全部人员列表为派发或转发选择一个接收人。 | 目标部署读取已验证；当前产品 capability 未实现。搜索、筛选等交互未定义。 |
| 派发准备表面 | 逐条作出负责人决定，只把相同接收人的对象合并，并展示派发所需业务／运维负责人事实。 | 流程已确认；写域阻塞。 |
| 转发准备表面 | 从当前用户可见漏洞主动选择对象，选择接收人，按相同接收人合并。 | 流程已确认；写域阻塞。 |
| 直接延时准备表面 | 管理员处理单条漏洞，查看当前状态，填写新期限和可选原因。 | 流程已确认；状态集合和期限约束未验证，写域阻塞。 |
| 误报准备表面 | 对操作人确认属于自己负责的一条漏洞准备“误报”状态变化。 | 流程已确认；权限和状态值域未验证，写域阻塞。 |
| 二次确认表面 | 逐条展示统一卡片及目标负责人／目标状态／新期限与原因，支持确认或取消。 | 内容与安全行为已确认；具体容器和导航未定义。 |
| 执行与回读结果表面 | 按漏洞逐条展示最终事实和成功／失败／待排查；合并操作保留部分成功。 | 结果规则已确认；回读等待、中间态和恢复交互未定义。 |
| 共用状态呈现 | 在相关表面区分空结果、加载、无权限、字段缺失、数据不足、外部失败、状态不允许、部分失败和回读不一致。 | 状态分类大部分已确认；具体表现和部分文案未定义。 |

## 7. 仍需用户决定的 UX 问题

### 阻塞信息架构或关键流程闭合

1. 桌面 Workbench 的主入口是什么：以 Agent 对话发起任务、以明确任务页面发起，还是二者如何衔接？来源没有给出导航和首屏模型。
2. 派发以“全部新增队列”为明确入口；转发、误报和直接延时分别从哪里找到并进入一条已有漏洞，来源没有定义。
3. 统一漏洞事实是在高密度列表内直接完成判断，还是需要额外展开／详情表面？来源只规定字段和复用阶段。
4. 628 条级队列及 243 人列表如何浏览和定位：分页、滚动、搜索、筛选、快捷键均未确定，且不能因为数据量自行增加需求。
5. 多条漏洞逐条指定负责人后，如何让用户看清分组、发现不同负责人不能混合，并进入各自确认批次？约束已确定，交互尚未确定。
6. 二次确认采用何种界面容器与返回路径尚未确定；必须确保逐条明细可审阅、取消无写入，但不能从来源推断是弹窗还是页面。
7. 派发所需的业务系统负责人／运维负责人大量缺失时，用户是否仍可派发，还是必须阻止并标记“数据不足”？现有文档只要求展示和不得推断，没有决定可操作性。
8. 当前修复负责人、业务系统、业务负责人和运维负责人的缺失文案是否统一为空，还是区分“未分配”和“数据缺失”？来源同时出现“为空／未分配”，尚未形成唯一词汇规则。

### 阻塞状态与恢复体验

9. 加载、刷新、写入中、回读中和回读超时的状态与操作规则未定义。
10. 无权限、数据不足、查询失败、状态不允许的用户可见文案及下一步动作未定义。
11. 合并派发／转发部分失败后，是仅展示并联系负责人，还是允许对失败项重试／重新分组？重试、幂等和审计规则尚未确认，UX 不能先行承诺。
12. 除直接延时固定使用“延时成功”外，派发、转发和误报的成功提示文案未确认。
13. 结果表面关闭或离开后，用户从哪里重新找到该次逐条结果与待排查项？来源没有定义历史或审计界面，且不能擅自新增。

### 阻塞直接延时的可执行表单

14. 新期限可选范围、时间粒度、时区、是否必须晚于当前期限等约束尚无证据。
15. 可直接延时的原状态集合尚未在目标部署验证；在确定前不能形成可执行输入规则。

### 尚未形成的横向 UX 决策

16. 桌面端键盘操作、焦点顺序、读屏语义和最低可访问性要求尚未在来源中定义。
17. 界面语言、时间与日期格式、字段长文本／超长 POC 和 IP 展示规则尚未定义。
18. 本轮没有品牌、颜色、字体、间距、密度或视觉风格证据；这些全部留待用户在 DESIGN Discovery 中决定。

## 提取结论

- 需求已足以固定四条目标旅程的业务顺序、统一事实内容、人工决策边界、二次确认和回读成功条件。
- 当前可以闭合“精确新增查询—统一事实—人员读取”的只读 UX；不能把尚未通过门禁的写动作描述为当前可用能力。
- 进入 EXPERIENCE／DESIGN 定稿前，优先确认主入口、三个非新增动作的入口、统一事实承载方式、批量分组交互、缺失数据可操作性和写后恢复路径。
