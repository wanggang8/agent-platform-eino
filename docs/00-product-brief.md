# 产品简介

## 一句话

重新实现一个聊天优先的 Agent Workbench：用户用自然语言提出任务，系统可以调用工具、展示安全工具结果、请求审批或澄清、恢复执行，并提供审计和回放。

## 为什么重做

当前项目已经验证了 Agent runtime、Workbench、Fobrain、审批恢复、审计回放等能力。新版本用于练习和对比另一种架构：在不继承旧接口包袱的前提下，重新实现同等产品能力和体验，并比较代码复杂度、调试成本和框架收益。

这次是重构已有产品，不是新产品探索。最终必须恢复既有关键能力；实施上可以分阶段，但不能把后续阶段当成可选项。

技术实现不能照搬重构前的方案。新版本应使用全新设计去掉旧负债：通用执行能力采用成熟通用能力承载，产品契约、安全展示和业务能力接入边界由项目重新定义。

后续补充的工具清单、字段模板和验收场景，只用于描述新产品必须保留的能力与安全输出，不用于绑定旧代码结构或旧内部字段。

## 产品目标

- 用户能在 Workbench 中完成连续对话。
- 系统能根据用户意图调用工具，并把工具结果以卡片展示。
- 高风险操作必须先请求审批。
- 信息不明确时必须请求澄清，而不是猜测执行。
- 用户可以查看运行过程、工具证据、审计和回放。
- 外部系统可以通过 Action API 直接调用同一套 Agent 能力。
- 前端视觉保持当前 Workbench 的三栏工作台体验。

## 产品原则

- 聊天优先，内部事件不直接打扰用户。
- 工具结果先结构化，再展示。
- 审批、澄清、恢复都要有明确状态。
- Workbench 和外部 API 看到的是同一套安全产品事实。
- Fobrain 是业务能力样板，但不能写进 runtime 内核。

## 本次完整目标

本次完整重构目标是 P0 + P1 + P2 全部完成：

- P0：最小产品闭环。
- P1：产品级运行能力。
- P2：既有业务能力恢复。

只有 P0、P1、P2 全部通过，才算完整重构完成。只完成 P0/P1 可以证明新架构可行，但不能声明能力等价，也不能替换当前产品基线。

## 阶段性成功状态

P0/P1 成功不是“功能全量复制”，而是证明新架构能稳定跑通：

- 普通聊天。
- 工具调用。
- 工具卡展示。
- 审批与恢复。
- 审计与回放。
- Action API。
- Workbench 视觉不跑偏。

Fobrain 3 个只读工具只是架构 PoC；要声明产品能力可比和重构完成，必须通过 Fobrain 完整恢复门禁。
